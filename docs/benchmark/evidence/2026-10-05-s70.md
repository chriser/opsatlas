# REF S70 #2206: the test suite never reaches a live service; emergency recovery kept for the host's command (5 October 2026)

Two follow-ups recorded on REF F11 #2170, neither needing a decision. Tests only: no production code changes.

## Why

- **Live services.** The independent review of Bugs #2191 and #2192 found tests reaching for the local model server at
  `127.0.0.1:11434`; they pass when refused. Nothing in the suite stopped a test reaching a live service on this Mac:
  only the Sales workspace builder refused the network. Every gate run, and every reviewer's, should leave the live
  services alone.
- **Emergency recovery.** S68's IR2: `Identity.emergency_recovery` has no actor and no permission check, and no check
  limited its callers.

## Measured before the change

The full suite ran on main (`1beda5c`) with a temporary hook that refused the live ports and logged every attempt, and
logged any connection off this machine:

- 1,583 passed plus 8 expected failures, the same as without the hook. No test depends on a live service.
- 13 connections to the model server (`11434`) from 12 tests in 11 files (Tibi, the Tibi gateway, owned work). Without
  the hook these reach the live server on every gate run.
- 1 connection to the diagram service (`5300`), from `tests/test_process_diagram_service_control.py`.
- No connection to any address off this machine.

## Promises

- **P1:** no test connects to a live service on this Mac, or to any address off it. Such a connection is refused at
  once, with a message naming the rule, from before any test module is imported. The ports:
  - the Sales workspace `8780`;
  - Tibi `8773`;
  - the diagram service `5300`;
  - a lone core `8010`;
  - a branch check `8791`;
  - OpsAtlas Classic `5200`;
  - the model servers: ours `11434`, and another project's `11435`.
- **P2:** every test passes with it, so no test depends on a live service.
- **P3:** among production modules, only the host's recovery command (`assistant.iam.__main__`) names
  `Identity.emergency_recovery`, besides IAM's service, which defines it. A new caller, or a listed caller that has
  gone, fails the gate.
- **P4:** no production code changes.

## What changed

- **`tests/live_guard.py`:** the ports, read from `assistant.settings` where it names them. `refused(address)` gives
  the reason a connection is refused. `install()` puts the check in front of the socket class's `connect` and
  `connect_ex`; `uninstall()` is used only for the guard's proof.
- **`tests/conftest.py`:** installs the guard after the throwaway data folder is set, and before a guard is switched
  off, so the guard's own proof can switch it off.
- **`tests/test_live_guard.py`:**
  - each live port, through `localhost` and `127.0.0.1`, is refused at once by both `connect` and `connect_ex`;
  - an address off the machine is refused;
  - a port of the test's own is still reachable;
  - the list covers every service the settings name.

  Each test first checks that the guard is installed. So with the guard switched off, it fails before trying any
  connection, and the proof reaches nothing live.
- **`tests/boundary_rules.py`, `SOLE_CALLERS`:**
  - a method kept for one caller is named by no other production module;
  - an attribute, or a string that is exactly its name, counts;
  - prose in a docstring does not;
  - a listed caller that no longer names it must leave the list.
- **`tests/test_boundaries.py`:** the rule against the code, and against planted code.
- **`tests/guard_register.py`:** two guards, each proven: the caller rule, and the live-service guard.
- **`docs/ways-of-working/Boundaries.md`:** the new rule.

## The #2191 test and the diagram service

The review asked to stub the diagram client in #2191's in-audience test. That test runs in the Sales workspace builder,
which already refuses the network, and the guard now refuses the diagram port in every test. It passes with the service
refused, so it never depends on it.

## The failure list

Tests only.

- **A crash, a restart, a failed write, two requests at once, the evidence changing, date and time, model output:** not
  involved. No state is written; the guard is a function in front of a socket call.
- **Duplicate or malformed input:** an address that is not a host and port (a local socket) goes ahead unchanged.
- **A dependency down or slow:** that is what the guard makes every live service look like, at once rather than after a
  timeout.

## Stated limits

- **A subprocess a test starts** is outside the guard. Today five test files start one:
  - the guard proofs: pytest itself, under the same conftest, so guarded;
  - ruff, in the boundary tests;
  - `git grep`, in the role catalogue's test;
  - `git`, and the worktree set-up script, in its own test;
  - a short Python check of the ontology's alias order.

  None of them connects anywhere.
- **Name lookups** are not blocked, only connections. No test was seen connecting off the machine.
- **Another loopback address** (`127.0.0.2`, `0.0.0.0`) counts as off the machine and is refused, which is stricter
  than needed.
- **A method name built at run time** (`getattr(iam, "emergency_" + "recovery")`) escapes the caller rule, as computed
  names escape the other rules.
