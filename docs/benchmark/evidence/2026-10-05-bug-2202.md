# Bug #2202: any space's owner can lift another space's document restriction (design, 5 October 2026)

**How it was found.** The design red team on Bug #2199 (round 2, 5 October 2026, night) found it, with a probe. Tier:
full (access, IAM, REF S13). This page is the design, for its red team on paper before anything is built.

## What happens today

- **The table.** IAM keeps one row per restricted document or folder in `resource_policies`, keyed by
  `(resource_type, resource_id)` only, with a `space_id` column (`src/assistant/iam/store.py`).
- **The change path.** `IdentityService.restrict(actor, space_id, type, id, audience, reason)` (`service.py`) does this:
  1. It checks `resources.permissions.manage` in the space named in the request's path.
  2. It looks up the row by `(type, id)` alone.
  3. It updates the row, rewriting `space_id` to the caller's space.

  It never checks that the document or folder is in that space. The route is
  `PUT /api/iam/spaces/{space_id}/restrictions/{type}/{id}` (`src/assistant/api/routes_iam.py`).
- **The effect.** The owner of the organisation space Acme lifted a restricted Product Guide document's restriction from
  Acme's path, and a guide reader then read the document. The audit event names Acme.
- **Reads look the row up two ways:**
  - **By space:** `restrictions(space_id)`, which `Visibility` uses for its fast path.
  - **By resource alone:** the policy's resource check (`policy.py`).

  So a row filed under the wrong space is seen by one and missed by the other.

## Promises

- **I1, a restriction belongs to the space that holds its resource.** A restriction is set, changed or lifted only
  through the space that holds the document or folder:
  - an existing row held by another space is refused, with nothing changed and no audit event;
  - a new row for a resource the space does not hold is refused too.

  The refusal is 404, the same as for a resource that does not exist, so another space's resources are not revealed.
- **I2, one place.** IAM's `restrict` enforces I1 for existing rows. For new rows, a resolver
  `holds(space_id, resource_type, resource_id) -> bool` is given to the IAM router by the app that builds it:
  - **a lone core:** its own space: the register for documents, the content library's groups for folders;
  - **the Sales workspace:** any of its cores, whichever core serves the request.
- **I3, nothing else changes.**
  - A space's owner restricting their own space's document or folder works exactly as today.
  - Reading restrictions, and evaluating them, are unchanged.
  - Rows already in the table are not rewritten.

## Design

- **In `IdentityService.restrict`:**
  - read the existing row's `space_id`;
  - if the row exists under another space, raise `IamError("NOT_FOUND", "No such document or folder in this space", 404)`
    before any write;
  - on update, keep the row's own `space_id`, which is now always the caller's, and stop rewriting it.
- **`build_iam_router(auth, holds=None)`.** The PUT route calls `holds(space_id, type, id)` first and answers 404 if it
  is false. With no resolver, it keeps today's behaviour, for tests that build the router alone.
  - **`create_app`** passes a resolver for its own space.
  - **The Sales app** passes a workspace resolver, built from its cores, to every core's IAM router, so a request served
    by any core answers for the space in its path.
- **The audit** records nothing for a refused change, as today for other refused requests.

## The failure list

- **Duplicate or stale input:** a second PUT for the same resource behaves as today in its own space. From another
  space it gets 404 each time.
- **Access changing mid-way:** a document moving to another space after its restriction was set. The row stays with
  the old space (Bug #2203 decides what moving does), and the old space can still change it. Stated.
- **Two requests at once:** IAM's writes are one transaction each.
- **A crash, a restart, a failed write:** one transaction. A refusal writes nothing.
- **A dependency down, date and time, model output:** not involved.

## Tests

- **The red team's probe:** Acme's owner lifting a guide document's restriction gets 404, the restriction stands, and
  the guide reader is still refused. It fails before the fix.
- **A new restriction from another space** on a resource it does not hold: 404, no row.
- **The owner's own document and folder,** set, changed and lifted: unchanged, with the same audit events.
- **The Sales workspace:** a request for a playbook document served by the guide's core (no space header) still
  resolves the playbook.
- **A lone core** with no resolver: as today.
- **A guard:** the existing-row check switched off makes the probe test fail.

## Stated limits

- **A row that a cross-space change already wrote** keeps the space it was given. A one-off check of the live
  `iam.db` (read-only) reports any row whose resource is not in its space. A person fixes it.
- **Moving a document** does not move its restriction (Bug #2203).

## Impact map

- **Changed:**
  - `src/assistant/iam/service.py` (`restrict`);
  - `src/assistant/api/routes_iam.py` (the resolver);
  - `src/assistant/api/app.py` (a resolver for its own space);
  - `services/opsatlas_sales/app.py` (the workspace resolver for every core).
- **New:**
  - `tests/test_restriction_space.py`;
  - a guard entry.
- **Unchanged:**
  - IAM's schema (no migration);
  - the policy;
  - `Visibility`;
  - Tibi's engine.
- **S59's checks:** IAM imports nothing new, and the resolver is injected.
